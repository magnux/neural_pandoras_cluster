\section{Pandora's Cluster: A Worked Case Study}
\label{sec:evidence}

\subsection{What is lost when an image is cut into patches?}

Our dataset is a single RGB mosaic of Pandora's Cluster from the James Webb Space Telescope's NIRCam instrument~\cite{webb}. The image used in the experiment measures $17{,}644\times13{,}422$ pixels (236.8 megapixels). Dividing the mosaic into $32\times32$ patches lets the first network work on 3,072 channel values at a time, regardless of the size of the image. That leaves a different problem: where does each patch belong? The base grid has $419\times551$ sites, more than 230,000 locations. A patch can show a bright point against a dark background without revealing which part of the mosaic surrounds it.

Saving patch codes in source order supplies a placement map: a lookup gives the code to decode at any grid site. Here we want to generate a coherent view without consulting that map at sampling time. We use the map to build training examples for a second model, so it can learn which codes occur together (Fig.~\ref{fig:representation-model}).

\subsection{Encoding and reconstructing local appearance}

At the first stage, the encoder maps a $32\times32$ RGB patch to a code of 256 real values. A denoiser serves as the image decoder: given the code and a corrupted version of the patch, it predicts the clean pixels. We train the encoder and decoder together, comparing their reconstruction to the original patch in the feature space of a pretrained VGG network~\cite{vgg,perceptual}. Training ranges from lightly corrupted inputs, where much of the detail survives, to inputs dominated by noise, where the decoder must rely on the code. The code can also be kept while a damaged reconstruction is passed back to the decoder for repair.

The author recalls that early sampling runs with the patch model produced starry textures without reliably reproducing the cluster's larger structure. The training loss offers a reason: it rewards the reconstruction of each patch but never asks which patch should come next. We therefore turn to the behavior of the encoder across the mosaic. The bottleneck provides a compact record of the encoder's response to each crop, and the decoder gives us a way to inspect what that response retains.

\subsection{Generating the next window of codes}

We hold the trained encoder fixed and record its outputs on grids with slightly different origins. From these grids we take pairs of overlapping views, keeping the patch codes in spatial order. A second denoiser, the \emph{gencoder}, learns to predict the encoder's outputs for the second view from a corrupted window of outputs for the first. It has its own weights and receives no separate conditioning code: the code window itself is the state it updates. Each window contains $32\times32$ codes, which the image decoder can render as a $1024\times1024$ view.

How should the gencoder learn a continuation? Shifting the view by a whole patch would leave most codes in the target available to copy from a neighboring position in the input. Instead, we shift the underlying image crops by roughly eight pixels in each direction, one quarter of a patch, and encode them at the new positions. The two views cover much of the same sky, but every target code now describes a differently aligned patch. The gencoder must predict the codes for that next view, including changes within the overlap. It knows relative positions inside a window, but receives neither its global location in the mosaic nor the offset index: the content of the current window is its guide. Appendix~\ref{sec:implementation} gives the precise crop and training rules.

\subsection{Rendering a sequence}

The video sampler starts with a canvas of latent noise. At each frame it adds fresh noise to overlapping windows of the current canvas and applies the gencoder to them. Where several windows predict the same site, their predictions are averaged to form the next canvas. There is no explicit translation of the canvas; a consistent motion from frame to frame must come from the displaced target learned in training.

The image decoder renders each site as an RGB patch, using the generated code and one call from fresh pixel noise. Tiling the patches and cropping the edges yields a $1920\times1080$ frame (width by height). Only the latent canvas carries over to the next frame. This distinction matters for interpreting the sequence: it exercises repeated prediction in code space, while pixel-space regeneration would require returning a damaged reconstruction to the decoder.

\subsection{Coherence and loss of place}

In the author's account, sampling with the gencoder produced extended views in which structure remained coherent across many patches and resembled the mosaic. The moving images sometimes had a noisy, VHS-like texture. Occasionally a sequence seemed to leave one part of the sky and resume in another, an effect the author calls \emph{teleportation}.

One possible explanation is ambiguity of place. Two dark or visually similar regions can have different surroundings; without a global address, either continuation may fit the available content. The existing record does not establish this mechanism or identify a jump's destination. The video overlay reports mean squared latent activation, not entropy. The archived training traces show decreasing loss on the reconstruction and shifted-prediction tasks (Appendix~\ref{sec:traces}); they do not measure recovery of the original layout or repair after damage. The sampled stills and video are absent from this release, and the early sampler survives in a mixed-version notebook (Appendix~\ref{sec:archive}). The contrast with patch sampling is a qualitative observation from the original runs.
